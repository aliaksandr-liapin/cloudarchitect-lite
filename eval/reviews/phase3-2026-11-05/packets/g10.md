# Review packet, group 10

Scenarios in this packet: fraud-model-serving, brochure-site, product-search. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

### Design B

**Requirements**

- R1 [constraint, confirmed] Relational database remains the source of truth for the 2 million products.
- R2 [functional, confirmed] Shoppers need fast full-text search over products.
- R3 [functional, confirmed] Search must tolerate typos.
- R4 [functional, confirmed] Search must support filters by brand, price, and size.
- R5 [non-functional, confirmed] Product pages are read far more often than they change, so reads must be served efficiently and cached where appropriate.
- R6 [non-functional, confirmed] Price updates must appear in search results within one minute of the change.
- R7 [constraint, confirmed] The web API runs in containers and must be deployable as containerized workloads.
- R8 [functional, inferred] Search index must be kept in sync with the relational source of truth as products change.
- R9 [non-functional, inferred] Search latency should stay low under shopper traffic, with read-heavy scaling.
- R10 [functional, inferred] Initial bulk load of the 2 million products into the search index before go-live, plus a way to reindex.
- R11 [non-functional, inferred] Web API is reachable by shoppers over HTTPS and protected from common web exploits.
- R12 [non-functional, inferred] Failed sync events must be retained and alarmed on so no price change is silently lost.
- R13 [non-functional, inferred] Data stores are encrypted at rest and database credentials are held in a secrets store.
- R14 [non-functional, inferred] The web API tier and database must remain available if one Availability Zone fails.
