# Review packet, group 8

Scenarios in this packet: order-events-cross-region, nightly-reports, support-chatbot. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: order-events-cross-region

**User prompt**

> An online shop accepts orders through an API. After an order is placed, payment capture, inventory reservation and the confirmation email must happen independently, so a failure in one does not block the others. Failed steps must be retried and never silently lost. Orders are looked up by order ID.

**Enabled priorities** (chosen by the user with one-click toggles)

- Recover in a second AWS Region: data is replicated cross-region and the design can be restored there.

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Accept orders through an API

- R3 [non-functional, confirmed] A failure in one step (payment capture, inventory reservation, confirmation email) must not block the others
- R4 [non-functional, confirmed] Failed steps must be retried
- R5 [non-functional, confirmed] Failed steps must never be silently lost; failures must be durably recorded and surfaced
- R6 [functional, confirmed] Orders can be looked up by order ID
- R7 [non-functional, inferred] Order placement should be decoupled from downstream processing via asynchronous events or queues
- R8 [non-functional, inferred] Retried messages that still fail should be isolated in a dead-letter queue for inspection and replay
- R9 [non-functional, inferred] Order data should be persisted durably so lookup by order ID survives component failures
- R10 [non-functional, confirmed] Recover in a second AWS Region: data is replicated cross-region and the design can be restored there.
- R11 [non-functional, inferred] Order API callers must be authenticated, and order lookup must be limited to the owning customer
- R12 [non-functional, inferred] Each downstream consumer must be idempotent, keyed by order ID, so retries do not double-charge, double-reserve or double-send
- R13 [non-functional, inferred] Operators must be alerted when messages land in a dead-letter queue and have a way to inspect and replay them

## Scenario: nightly-reports

**User prompt**

> Every night at 02:00 we need to generate PDF sales reports from our existing Aurora PostgreSQL database, store them for a year, and email a download link to 40 regional managers. The job takes about 25 minutes. Keep it simple and cheap.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Generate PDF sales reports every night at 02:00 from the existing Aurora PostgreSQL database
- R2 [non-functional, confirmed] Store generated reports for one year
- R3 [functional, confirmed] Email a download link for each report to 40 regional managers
- R4 [non-functional, confirmed] Report generation job takes about 25 minutes per run
- R5 [constraint, confirmed] Keep the solution simple and low cost
- R6 [constraint, inferred] Use the existing Aurora PostgreSQL database as the data source without migrating it
- R7 [non-functional, inferred] Download links should be secure and expire after a period, so reports are not publicly accessible
- R8 [non-functional, inferred] Scheduled job must complete reliably within the nightly window and retry on failure
- R9 [non-functional, inferred] Alarm on failed nightly runs and on failed email sends so the team learns about a missed report before managers do
- R10 [non-functional, inferred] Report generation is idempotent: a retried run overwrites the same per-day object keys instead of creating duplicates
- R11 [constraint, inferred] Each compute component uses its own least-privilege IAM role; the database is reachable only from the report task

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - Region (same as Aurora) (region) [C2]
    - Existing VPC (vpc) [C3]
      - Public subnet (subnet, public) [C4]
      - Private subnet (database) (subnet, private) [C5]

**Nodes**

- **Nightly 02:00 schedule** [N1] - service: Amazon EventBridge
  - purpose: Starts the nightly report run at 02:00
  - rationale: EventBridge Scheduler is serverless, cheap and supports cron expressions with a retry policy for the start call
  - placed in: Region (same as Aurora)
  - satisfies: R1, R5
- **Report workflow** [N2] - service: AWS Step Functions
  - purpose: Runs the report task, retries on failure, then triggers the email step
  - rationale: Step Functions waits for the 25-minute ECS task (run-and-wait), applies retries and records each step's status, which keeps the job reliable within the nightly window without an always-on orchestrator
  - placed in: Region (same as Aurora)
  - satisfies: R1, R4, R8, R9, R10
- **PDF report task** [N3] - service: AWS Fargate
  - purpose: Queries Aurora for the previous day's sales, renders PDF reports and writes them to S3
  - rationale: Fargate runs a container for about 25 minutes without managing servers and is billed only while running; Lambda cannot run this long
  - placed in: Public subnet
  - satisfies: R1, R4, R5, R8, R10, R11
- **Existing Aurora PostgreSQL** [N4] - service: Amazon Aurora
  - purpose: Source of sales data, used in place without migration
  - rationale: The existing database is used as-is so no data is moved, meeting the no-migration requirement; it stays in a private subnet
  - placed in: Private subnet (database)
  - satisfies: R1, R6
- **Report bucket** [N5] - service: Amazon S3
  - purpose: Stores generated PDF reports for one year with a lifecycle expiry
  - rationale: S3 is durable, low cost and keeps reports private; a lifecycle rule removes them after 365 days, and the bucket is never public
  - placed in: Region (same as Aurora)
  - configuration encryption: AWS-managed
  - satisfies: R2, R5, R7
- **Email sender** [N6] - service: AWS Lambda
  - purpose: Reads the recipient list, creates a presigned download link per report and sends emails
  - rationale: A short Lambda runs once per night after the report task, which is cheaper than a server and fits well under its time limit
  - placed in: Region (same as Aurora)
  - satisfies: R3, R5, R7, R11
- **Amazon SES** [N7] - service: Amazon SES
  - purpose: Sends the emails with download links to the managers
  - rationale: SES is the low-cost, managed email service for transactional mail at this volume (40 recipients)
  - placed in: Region (same as Aurora)
  - satisfies: R3, R5
- **CloudWatch alarms and logs** [N8] - service: Amazon CloudWatch
  - purpose: Collects logs and metrics from the workflow, task and sender, and alarms on failed runs
  - rationale: Required for observability: alarms on failed executions and missed runs let the team act before managers notice a missing report
  - placed in: Region (same as Aurora)
  - satisfies: R8, R9
- **Regional managers (40)** [N9] - EXTERNAL third-party: Regional managers (40)
  - purpose: Receive the nightly email and download their reports
  - rationale: Recipients outside the AWS solution
  - satisfies: R3, R7
- **Operations team** [N10] - EXTERNAL third-party: Operations team
  - purpose: Monitors alarms for failed runs
  - rationale: Receives alarm notifications for missed or failed reports
  - satisfies: R9

**Edges**

  - satisfies: R1

  - satisfies: R1, R4, R8

  - satisfies: R1, R6

  - satisfies: R3, R7

  - satisfies: R3

  - satisfies: R3, R7
- Regional managers (40) -> Report bucket (read, HTTPS): Download report via expiring link
  - satisfies: R7

  - satisfies: R8, R9
- CloudWatch alarms and logs -> Operations team (other): Alarm notification
  - satisfies: R9

- **Nightly 02:00 schedule** [N1] - service: Amazon EventBridge
  - purpose: Starts the nightly report run at 02:00
  - rationale: EventBridge Scheduler is serverless, cheap and supports cron expressions with a retry policy for the start call
  - placed in: Region (same as Aurora)
  - satisfies: R1, R5
- **Report workflow** [N2] - service: AWS Step Functions
  - purpose: Runs the report task, retries on failure, then triggers the email step
  - rationale: Step Functions waits for the 25-minute ECS task (run-and-wait), applies retries and records each step's status, which keeps the job reliable within the nightly window without an always-on orchestrator
  - placed in: Region (same as Aurora)
  - satisfies: R1, R4, R8, R9, R10
- **PDF report task** [N3] - service: AWS Fargate
  - purpose: Queries Aurora for the previous day's sales, renders PDF reports and writes them to S3
  - rationale: Fargate runs a container for about 25 minutes without managing servers and is billed only while running; Lambda cannot run this long
  - placed in: Public subnet
  - satisfies: R1, R4, R5, R8, R10, R11
- **Existing Aurora PostgreSQL** [N4] - service: Amazon Aurora
  - purpose: Source of sales data, used in place without migration
  - rationale: The existing database is used as-is so no data is moved, meeting the no-migration requirement; it stays in a private subnet
  - placed in: Private subnet (database)
  - configuration encryption: AWS-managed
  - satisfies: R1, R6
- **Report bucket** [N5] - service: Amazon S3
  - purpose: Stores generated PDF reports for one year with a lifecycle expiry
  - rationale: S3 is durable, low cost and keeps reports private; a lifecycle rule removes them after 365 days, and the bucket is never public
  - placed in: Region (same as Aurora)
  - configuration encryption: AWS-managed
  - satisfies: R2, R5, R7
- **Email sender** [N6] - service: AWS Lambda
  - purpose: Reads the recipient list, creates a presigned download link per report and sends emails
  - rationale: A short Lambda runs once per night after the report task, which is cheaper than a server and fits well under its time limit
  - placed in: Region (same as Aurora)
  - satisfies: R3, R5, R7, R11
- **Amazon SES** [N7] - service: Amazon SES
  - purpose: Sends the emails with download links to the managers
  - rationale: SES is the low-cost, managed email service for transactional mail at this volume (40 recipients)
  - placed in: Region (same as Aurora)
  - satisfies: R3, R5
- **CloudWatch alarms and logs** [N8] - service: Amazon CloudWatch
  - purpose: Collects logs and metrics from the workflow, task and sender, and alarms on failed runs
  - rationale: Required for observability: alarms on failed executions and missed runs let the team act before managers notice a missing report
  - placed in: Region (same as Aurora)
  - satisfies: R8, R9
- **Regional managers (40)** [N9] - EXTERNAL third-party: Regional managers (40)
  - purpose: Receive the nightly email and download their reports
  - rationale: Recipients outside the AWS solution
  - satisfies: R3, R7
- **Operations team** [N10] - EXTERNAL third-party: Operations team
  - purpose: Monitors alarms for failed runs
  - rationale: Receives alarm notifications for missed or failed reports
  - satisfies: R9
