# Review packet, group 5

Scenarios in this packet: support-chatbot, product-search, nightly-reports-serverless. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

**User prompt**

> We want a customer support chat assistant that answers questions using our 20,000 product manuals (PDFs). Answers must cite the manual they came from. Only logged-in customers can use it, conversation history is kept for 30 days, and we prefer a managed foundation model rather than hosting our own.

Product pages are read far more often than they change, and price updates must appear in search within a minute. The web API runs in containers.

**Enabled priorities** (chosen by the user with one-click toggles)

## Scenario: nightly-reports-serverless

**User prompt**

> Every night at 02:00 we need to generate PDF sales reports from our existing Aurora PostgreSQL database, store them for a year, and email a download link to 40 regional managers. The job takes about 25 minutes. Keep it simple and cheap.

**Enabled priorities** (chosen by the user with one-click toggles)

- Prefer serverless and fully managed services (Lambda, API Gateway, DynamoDB, Fargate, Step Functions) over servers to manage.

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Generate PDF sales reports every night at 02:00.
- R2 [constraint, confirmed] Use the existing Aurora PostgreSQL database as the report data source.
- R3 [constraint, confirmed] The report-generation job takes approximately 25 minutes to run.
- R4 [functional, confirmed] Store generated reports for one year.
- R5 [functional, confirmed] Email a download link for the reports to 40 regional managers.
- R6 [non-functional, confirmed] Keep the solution simple and inexpensive.
- R7 [non-functional, inferred] The report-generation process must support a run of approximately 25 minutes without timing out.
- R8 [functional, inferred] How should managers access the emailed download links? (decided by the architect)
- R9 [functional, inferred] Should report emails use an existing email service, or can the solution use Amazon SES? (decided by the architect)
- R10 [non-functional, confirmed] Prefer serverless and fully managed services (Lambda, API Gateway, DynamoDB, Fargate, Step Functions) over servers to manage.
- R11 [functional, inferred] Managers need a time-limited way to download reports without AWS accounts.
- R12 [functional, inferred] Generated reports must be automatically removed after one year.
- R13 [non-functional, inferred] The scheduled report run must be monitored, with failures visible to operators.

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - AWS Region (region) [C2]
    - Report workload VPC (vpc) [C3]
      - Availability Zone A (availability-zone) [C4]
        - Public subnet for Fargate task (subnet, public) [C5]
        - Private subnet for existing Aurora (subnet, private) [C6]

**Nodes**

- **Nightly 02:00 schedule** [N1] - service: Amazon EventBridge
  - purpose: Starts the report task once each night at 02:00 in the configured time zone.

### Design B

**Requirements**

- R1 [functional, confirmed] Generate PDF sales reports every night at 02:00.
- R2 [constraint, confirmed] Use the existing Aurora PostgreSQL database as the report data source.
- R3 [constraint, confirmed] The report-generation job takes approximately 25 minutes to run.
- R4 [functional, confirmed] Store generated reports for one year.
- R5 [functional, confirmed] Email a download link for the reports to 40 regional managers.
- R6 [non-functional, confirmed] Keep the solution simple and inexpensive.
- R7 [non-functional, inferred] The report-generation process must support a run of approximately 25 minutes without timing out.
- R8 [functional, inferred] How should managers access the emailed download links? (decided by the architect)
- R9 [functional, inferred] Should report emails use an existing email service, or can the solution use Amazon SES? (decided by the architect)
- R10 [non-functional, confirmed] Prefer serverless and fully managed services (Lambda, API Gateway, DynamoDB, Fargate, Step Functions) over servers to manage.
- R11 [functional, inferred] Managers need a time-limited way to download reports without AWS accounts.
- R12 [functional, inferred] Generated reports must be automatically removed after one year.
- R13 [non-functional, inferred] The scheduled report run must be monitored, with failures visible to operators.
