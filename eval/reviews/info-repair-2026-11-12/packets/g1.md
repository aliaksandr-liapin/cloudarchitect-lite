# Review packet, group 1

Scenarios in this packet: myblog-backups, product-search-cost, legacy-lift-and-shift. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: product-search-cost

**User prompt**

> Our e-commerce site has 2 million products in a relational database that stays the source of truth. Shoppers need fast full-text search with typo tolerance and filters (brand, price, size). Product pages are read far more often than they change, and price updates must appear in search within a minute. The web API runs in containers.

**Enabled priorities** (chosen by the user with one-click toggles)

- Minimize cost: choose the cheapest reasonable options and scale to zero where possible.

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [constraint, confirmed] Keep the existing relational database as the source of truth for 2 million products.
- R2 [functional, confirmed] Provide fast full-text product search with typo tolerance.
- R3 [functional, confirmed] Support search filters by brand, price, and size.
- R4 [non-functional, confirmed] Serve product page reads, which are far more frequent than writes.
- R5 [non-functional, confirmed] Propagate price updates to search results within one minute.
- R6 [constraint, confirmed] Run the web API in containers.
- R7 [functional, inferred] Sync product changes from the relational database to the search index.
- R8 [non-functional, inferred] Cache product page reads to offload the relational database.
- R9 [non-functional, inferred] Keep search latency low for shoppers during peak traffic.
- R10 [non-functional, confirmed] Minimize cost: choose the cheapest reasonable options and scale to zero where possible.
- R11 [non-functional, inferred] Observability: monitor API latency, search latency, sync lag and sync failure queue depth
- R12 [functional, inferred] Invalidate cached product pages when a product changes so shoppers do not see stale prices
- R13 [functional, inferred] Initial bulk load of all 2 million products from the relational database into the search index
- R14 [non-functional, inferred] Failed sync attempts are retried and parked in a queue with an alarm so index updates are not silently lost

## Scenario: legacy-lift-and-shift

**User prompt**

> We are migrating a legacy Java monolith from our data center. Today it runs on two virtual machines behind a hardware load balancer with a MySQL database. We must move within three months with minimal code changes, keep it highly available across two availability zones, and stop managing database backups ourselves. Shared file uploads are stored on an NFS share.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.
