# Review packet, group 2

Scenarios in this packet: myblog-backups, nightly-reports, support-chatbot. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: nightly-reports

**User prompt**

> Every night at 02:00 we need to generate PDF sales reports from our existing Aurora PostgreSQL database, store them for a year, and email a download link to 40 regional managers. The job takes about 25 minutes. Keep it simple and cheap.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Generate PDF sales reports nightly at 02:00 from the existing Aurora PostgreSQL database
- R2 [functional, confirmed] Store generated reports for one year
- R3 [functional, confirmed] Email a download link to 40 regional managers after each report is generated
- R4 [non-functional, confirmed] Report generation job takes about 25 minutes and must complete reliably within the nightly run
- R5 [constraint, confirmed] Keep the solution simple and low cost
- R6 [constraint, confirmed] Reuse the existing Aurora PostgreSQL database as the data source
- R7 [non-functional, inferred] Delete reports automatically after one year retention period
- R8 [non-functional, inferred] Download links should be secure and time-limited so only intended managers can access reports
- R9 [non-functional, inferred] Alert operators if the nightly job fails or does not finish
- R10 [functional, inferred] How should managers access the downloaded reports? (decided by the architect)
- R11 [functional, inferred] Which email sending approach should be used for the manager emails? (decided by the architect)
- R12 [functional, inferred] Should reports older than one year be deleted automatically or archived to cheaper storage? (decided by the architect)
- R13 [functional, inferred] Manager notification must be idempotent so Lambda retries do not email managers twice for the same report run
- R14 [non-functional, inferred] Generated reports must be encrypted at rest and reachable only through time-limited links
- R15 [non-functional, inferred] The 02:00 report queries must not degrade the production workload on the existing Aurora cluster

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - Region (region) [C2]
    - Report VPC (vpc) [C3]
      - Public subnet (subnet, public) [C4]
      - Private subnet (subnet, private) [C5]

**Nodes**

- **02:00 nightly schedule** [N1] - service: Amazon EventBridge
  - purpose: Starts the report job every night at 02:00
  - rationale: A scheduled rule is the simplest serverless trigger and needs no always-on compute
  - placed in: Region
  - satisfies: R1, R5
- **PDF report job** [N2] - service: AWS Fargate
  - purpose: Queries Aurora, renders PDF sales reports, writes them and a manifest to S3
  - rationale: The job runs about 25 minutes, which exceeds Lambda's 15-minute limit; Fargate runs it on demand with no servers to manage
  - placed in: Private subnet
  - satisfies: R1, R2, R4, R5, R6, R15
- **Existing Aurora PostgreSQL** [N3] - service: Amazon Aurora
  - purpose: Existing sales database used as the report data source
  - rationale: Reusing the existing database avoids copying data and extra cost
  - placed in: Private subnet
  - configuration encryption: AWS-managed
  - satisfies: R1, R6, R15
- **NAT Gateway** [N4] - service: NAT Gateway
  - purpose: Egress for the Fargate task to S3 and CloudWatch
  - rationale: Private-subnet tasks need outbound access; a single NAT keeps cost low
  - placed in: Public subnet
  - satisfies: R4, R5
- **Report bucket** [N5] - service: Amazon S3
  - purpose: Stores PDF reports and the manager manifest for one year
  - rationale: S3 is the cheapest durable store for files; lifecycle expiry enforces the one-year retention and encryption protects data at rest
  - placed in: Region
  - configuration encryption: AWS-managed
  - satisfies: R2, R7, R8, R10, R12, R14
- **Notify managers** [N6] - service: AWS Lambda
  - purpose: Reads the manifest, creates presigned links and sends one email per manager
  - rationale: Event-driven Lambda is cheap for 40 emails a night and needs no server
  - placed in: Region
  - satisfies: R3, R8, R10, R13
- **Amazon SES** [N7] - service: Amazon SES
  - purpose: Sends the download-link emails
  - rationale: SES is the lowest-cost managed email service for low volume
  - placed in: Region
  - satisfies: R3, R5, R11
- **Operator alerts** [N8] - service: Amazon SNS
  - purpose: Delivers failure and missed-completion alerts to operators
  - rationale: SNS fans out alerts to operator email or chat with minimal cost
  - placed in: Region
  - satisfies: R9
- **Job logs and completion alarm** [N9] - service: Amazon CloudWatch
  - purpose: Collects job logs and metrics and alarms if the job fails or does not finish
  - rationale: CloudWatch is the native way to alert on a missing completion signal
  - placed in: Region
  - satisfies: R4, R9
- **Regional managers** [N10] - EXTERNAL third-party: Regional managers
  - purpose: Receive the email and download their region's report
  - rationale: The 40 regional managers are the end users of the reports
  - satisfies: R3, R8, R10

**Edges**

- 02:00 nightly schedule -> PDF report job (invoke): Start nightly run at 02:00
  - satisfies: R1, R4
- PDF report job -> Existing Aurora PostgreSQL (read, PostgreSQL): Query sales data
  - satisfies: R1, R6, R15
- PDF report job -> Report bucket (write): Store PDFs and manifest
  - satisfies: R1, R2, R12
- PDF report job -> NAT Gateway (other): Egress to S3 and CloudWatch
  - satisfies: R4, R5
- PDF report job -> Job logs and completion alarm (other): Job logs and completion metric
  - satisfies: R4, R9
- Report bucket -> Notify managers (event): Manifest created
  - satisfies: R3, R13
- Notify managers -> Report bucket (read): Read manifest
  - satisfies: R3, R8
- Notify managers -> Amazon SES (invoke): Send email with link
  - satisfies: R3, R11, R13
- Amazon SES -> Regional managers (other): Email with download link
  - satisfies: R3, R8, R11
- Regional managers -> Report bucket (read): Download report via presigned URL
  - satisfies: R2, R8, R10
- Notify managers -> Operator alerts (event): Failed notification invocations
  - satisfies: R9, R13
- Job logs and completion alarm -> Operator alerts (other): Alarm notification
  - satisfies: R9

## Scenario: support-chatbot

**User prompt**

> We want a customer support chat assistant that answers questions using our 20,000 product manuals (PDFs). Answers must cite the manual they came from. Only logged-in customers can use it, conversation history is kept for 30 days, and we prefer a managed foundation model rather than hosting our own.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Provide a customer support chat assistant that answers questions using the 20,000 product manuals.
- R2 [functional, confirmed] Answers must cite the manual they came from.
- R3 [functional, confirmed] Only logged-in customers can use the assistant.
- R4 [constraint, confirmed] Keep conversation history for 30 days.
- R5 [constraint, confirmed] Use a managed foundation model rather than hosting a model.
- R6 [functional, inferred] Make manual content searchable so answers can be grounded in relevant passages and linked to their source manuals.
- R7 [functional, inferred] Ingest and process PDF manuals for use by the assistant.
- R8 [functional, inferred] How do customers log in, and should the assistant use your existing identity system? (decided by the architect)
- R9 [functional, inferred] What usage volume should the system support? This affects model capacity, retrieval sizing, and cost. (decided by the architect)
- R10 [functional, inferred] Are the manuals text-searchable PDFs, or do some require OCR because they are scanned? (decided by the architect)
- R11 [functional, inferred] Provide a customer-facing chat interface and authenticated API for asking questions and receiving answers with source-manual citations.
- R12 [functional, inferred] Extract and index manual content with source metadata so retrieval can return relevant passages and the manual citation.
- R13 [functional, inferred] Retain each customer's conversation history for 30 days, then expire it.
- R14 [functional, inferred] Use a managed AWS foundation model and retrieve relevant manual passages to ground answers.

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - Primary AWS Region (region) [C2]

**Nodes**

- **Customer** [N1] - EXTERNAL user: Logged-in customer
  - purpose: Uses the chat assistant and views answers with source-manual citations.
  - rationale: The customer is the end user of the support assistant.
  - satisfies: R1, R2, R3, R11
- **Chat client** [N2] - EXTERNAL client-app: Customer web chat client
  - purpose: Provides the customer-facing chat experience.
  - rationale: A client application is needed for customers to interact with the assistant.
  - satisfies: R1, R2, R3, R11
- **Customer sign-in** [N3] - service: Amazon Cognito
  - purpose: Authenticates customers and issues tokens for API access.
  - rationale: Cognito provides a managed customer identity service for the assumed sign-in approach.
  - placed in: Primary AWS Region
  - satisfies: R3, R8
- **Chat API** [N4] - service: Amazon API Gateway
  - purpose: Accepts authenticated chat requests and returns answers with citations.
  - rationale: A regional HTTP API is a simple managed entry point for the chat backend; Cognito authorization restricts use to logged-in customers.
  - placed in: Primary AWS Region
  - configuration apiType: HTTP
  - configuration authorizer: Cognito user pool
  - satisfies: R1, R2, R3, R9, R11
- **Chat and retrieval handler** [N5] - service: AWS Lambda
  - purpose: Uses the authenticated customer identity to retrieve relevant passages, invoke the model, and return an answer with source-manual citations.
  - rationale: Lambda provides serverless request processing and can apply customer-scoped history and retrieval logic.
  - placed in: Primary AWS Region
  - satisfies: R1, R2, R3, R4, R5, R6, R9, R11, R12, R13, R14
- **Managed foundation model** [N6] - service: Amazon Bedrock
  - purpose: Generates support answers grounded in retrieved manual passages.
  - rationale: Amazon Bedrock provides managed foundation-model inference without hosting a model.
  - placed in: Primary AWS Region
  - satisfies: R1, R2, R5, R6, R14
- **Manual PDF archive** [N7] - service: Amazon S3
  - purpose: Stores the source PDFs for initial bulk ingestion and ongoing additions.
  - rationale: S3 provides durable object storage for the supplied manuals and preserves source objects for citation and reprocessing.
  - placed in: Primary AWS Region
  - satisfies: R1, R2, R7, R12
- **PDF extraction and indexing worker** [N8] - service: AWS Lambda
  - purpose: Extracts selectable text from PDFs, splits it into passages, preserves source-manual metadata, creates embeddings, and indexes content.
  - rationale: A serverless worker is sufficient for processing new PDF objects; the initial corpus can be loaded as a controlled bulk ingestion.
  - placed in: Primary AWS Region
  - satisfies: R1, R2, R6, R7, R10, R12
- **Manual search and conversation index** [N9] - service: Amazon OpenSearch Service
  - purpose: Stores searchable manual passages and source metadata, and stores conversation history with customer identity and timestamps.
  - rationale: OpenSearch supports text and vector retrieval for grounding answers and can hold history with a 30-day retention policy.
  - placed in: Primary AWS Region
  - satisfies: R1, R2, R4, R6, R9, R12, R13
- **PDF ingestion failure queue** [N10] - service: Amazon SQS
  - purpose: Retains records for PDF-processing invocations that fail after asynchronous retries.
  - rationale: A queue provides a failure destination for asynchronous S3-triggered Lambda invocations so failed processing can be inspected and retried.
  - placed in: Primary AWS Region
  - satisfies: R7, R12
- **Logs and metrics** [N11] - service: Amazon CloudWatch
  - purpose: Collects application and ingestion logs, operational metrics, and alarms on PDF-ingestion failure queue depth.
  - rationale: Central observability supports operation of the chat API and PDF ingestion workflow, including detection of failed ingestion work.
  - placed in: Primary AWS Region
  - satisfies: R1, R7, R12

### Design B

**Requirements**

- R1 [functional, confirmed] Provide a customer support chat assistant that answers questions using the 20,000 product manuals.
- R2 [functional, confirmed] Answers must cite the manual they came from.
- R3 [functional, confirmed] Only logged-in customers can use the assistant.
- R4 [constraint, confirmed] Keep conversation history for 30 days.
- R5 [constraint, confirmed] Use a managed foundation model rather than hosting a model.
- R6 [functional, inferred] Make manual content searchable so answers can be grounded in relevant passages and linked to their source manuals.
- R7 [functional, inferred] Ingest and process PDF manuals for use by the assistant.
- R8 [functional, inferred] How do customers log in, and should the assistant use your existing identity system? (decided by the architect)
- R9 [functional, inferred] What usage volume should the system support? This affects model capacity, retrieval sizing, and cost. (decided by the architect)
- R10 [functional, inferred] Are the manuals text-searchable PDFs, or do some require OCR because they are scanned? (decided by the architect)
- R11 [functional, inferred] Provide a customer-facing chat interface and authenticated API for asking questions and receiving answers with source-manual citations.
- R12 [functional, inferred] Extract and index manual content with source metadata so retrieval can return relevant passages and the manual citation.
- R13 [functional, inferred] Retain each customer's conversation history for 30 days, then expire it.
- R14 [functional, inferred] Use a managed AWS foundation model and retrieve relevant manual passages to ground answers.
