# Review packet, group 10

Scenarios in this packet: nightly-reports, brochure-site, nightly-reports-serverless. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: nightly-reports

**User prompt**

> Every night at 02:00 we need to generate PDF sales reports from our existing Aurora PostgreSQL database, store them for a year, and email a download link to 40 regional managers. The job takes about 25 minutes. Keep it simple and cheap.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Generate PDF sales reports every night at 02:00 from the existing Aurora PostgreSQL database.
- R2 [constraint, confirmed] The report-generation job takes approximately 25 minutes.
- R3 [functional, confirmed] Store generated reports for one year.
- R4 [functional, confirmed] Email a download link for the reports to 40 regional managers.
- R5 [non-functional, confirmed] Keep the solution simple and inexpensive.
- R6 [functional, inferred] The process must run automatically on a nightly schedule and produce downloadable PDF reports.
- R7 [functional, inferred] How should regional managers access the report download links? (decided by the architect)
- R8 [functional, inferred] How should the report emails be sent? (decided by the architect)
- R9 [functional, inferred] Generated reports must be automatically deleted after one year to meet the retention requirement.
- R10 [functional, inferred] Report download links must grant managers time-limited access without requiring a separate user sign-in system.
- R11 [constraint, inferred] The scheduled job must run longer than Lambda's maximum invocation duration, so it needs a container task with sufficient runtime.

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - AWS Region (region) [C2]
    - Application VPC (vpc) [C3]
      - Availability Zone (availability-zone) [C4]
        - Private subnet (subnet, private) [C5]
        - Public subnet (subnet, public) [C6]

**Nodes**

- **Regional managers** [N1] - EXTERNAL user: 40 regional managers
  - purpose: Receive report emails and download reports using time-limited links.
  - rationale: Represents the email recipients and report downloaders.
  - satisfies: R4, R6, R7, R8
- **Nightly 02:00 schedule** [N2] - service: Amazon EventBridge
  - purpose: Starts the report task nightly.
  - rationale: A scheduled EventBridge rule is a simple way to invoke the container task on a recurring schedule.
  - placed in: AWS Region
  - satisfies: R1, R5, R6
- **ECS task definition** [N3] - service: Amazon ECS
  - purpose: Defines the report-generation container task.
  - rationale: ECS manages the task definition; Fargate runs the task without managing servers.
  - placed in: AWS Region
  - satisfies: R2, R5, R6
- **PDF report task** [N4] - service: AWS Fargate
  - purpose: Queries Aurora, generates PDFs, stores them, and emails download links.
  - rationale: A Fargate task can run for the approximately 25-minute job duration, unlike a single Lambda invocation.
  - placed in: Private subnet
  - satisfies: R1, R2, R3, R4, R5, R6, R11
- **Existing Aurora PostgreSQL** [N5] - service: Amazon Aurora
  - purpose: Source of sales data for report generation.
  - rationale: Uses the existing database as the report task's data source.
  - placed in: Private subnet
  - satisfies: R1
- **Sales reports bucket** [N6] - service: Amazon S3
  - purpose: Stores generated PDF reports and serves time-limited downloads.
  - rationale: S3 provides inexpensive object storage; lifecycle expiration enforces the one-year retention period.
  - placed in: AWS Region
  - configuration encryption: AWS-managed
  - satisfies: R3, R4, R5, R6, R9, R10
- **Amazon SES** [N7] - service: Amazon SES
  - purpose: Sends report notification emails to regional managers.
  - rationale: SES provides a straightforward managed email-sending service.
  - placed in: AWS Region
  - satisfies: R4, R5, R8
- **Task and schedule permissions** [N8] - service: AWS IAM
  - purpose: Grants the scheduler permission to start the task and the task permission to access required resources.
  - rationale: Least-privilege roles allow the scheduled task to read sales data, write reports, and send email.
  - placed in: AWS Cloud
  - satisfies: R1, R3, R4, R5, R6
- **NAT gateway** [N9] - service: NAT Gateway
  - purpose: Provides outbound access from the private task subnet to SES.
  - rationale: The task needs outbound connectivity to the SES email service while remaining in a private subnet.
  - placed in: Public subnet
  - satisfies: R4, R5
- **Task logs and alarms** [N10] - service: Amazon CloudWatch
  - purpose: Collects task logs and monitors scheduled task execution.
  - rationale: Provides basic operational visibility into report generation and failures.
  - placed in: AWS Region
  - satisfies: R1, R2, R5, R6

**Edges**

- Nightly 02:00 schedule -> ECS task definition (event, AWS service integration): Nightly scheduled task launch
  - satisfies: R1, R5, R6
- ECS task definition -> PDF report task (invoke, Fargate task launch): Run report task
  - satisfies: R1, R2, R6
- PDF report task -> Existing Aurora PostgreSQL (read, PostgreSQL): Read sales data
  - satisfies: R1
- PDF report task -> Sales reports bucket (write, HTTPS): Store generated PDFs and create time-limited download links
  - satisfies: R3, R4, R6, R9, R10
- PDF report task -> Amazon SES (invoke, HTTPS): Send report email with download link
  - satisfies: R4, R8, R10
- Amazon SES -> Regional managers (other, Email): Report download notification
  - satisfies: R4, R8
- Regional managers -> Sales reports bucket (read, HTTPS): Download PDF using presigned URL
  - satisfies: R4, R6, R7, R10
- Task and schedule permissions -> Nightly 02:00 schedule (other, IAM role): Allow scheduled task launch
  - satisfies: R1, R5, R6
- Task and schedule permissions -> PDF report task (other, IAM task role): Grant least-privilege access to data, S3, and SES
  - satisfies: R1, R3, R4, R5
- PDF report task -> NAT gateway (other, Outbound network): Reach SES from private subnet
  - satisfies: R4, R5
- PDF report task -> Task logs and alarms (write, CloudWatch Logs): Write task logs and execution status
  - satisfies: R1, R2, R5, R6

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Provide a marketing website with five static pages.
- R2 [functional, confirmed] Display the bakery's menu and opening hours.
- R3 [functional, confirmed] Serve the website under the bakery's own domain with HTTPS.
- R4 [constraint, confirmed] Support a few hundred website visits per day.
- R5 [constraint, confirmed] Keep ongoing costs to a few dollars per month.
- R6 [constraint, confirmed] Avoid infrastructure that requires server maintenance.

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - AWS Region (region) [C2]

**Nodes**

  - satisfies: R1, R2, R4

  - placed in: AWS Cloud
  - satisfies: R3
- **HTTPS website delivery** [N3] - service: Amazon CloudFront

  - satisfies: R1, R2, R3, R4, R5, R6, R7
- **Private static website files** [N4] - service: Amazon S3
  - purpose: Stores the five static pages and their menu and opening-hours content.

  - placed in: AWS Region
  - satisfies: R1, R2, R5, R6, R7
- **HTTPS certificate** [N5] - service: AWS Certificate Manager

  - satisfies: R3, R6
- **Operational monitoring** [N6] - service: Amazon CloudWatch
  - purpose: Provides basic visibility into website delivery metrics and logs where enabled.
  - rationale: Offers managed observability without requiring server maintenance.
  - placed in: AWS Region
  - satisfies: R4, R6

**Edges**

- Bakery customer -> Bakery domain DNS (other, DNS): Domain lookup
  - satisfies: R3
- Bakery customer -> HTTPS website delivery (invoke, HTTPS): Requests website pages
  - satisfies: R1, R2, R3, R4
- Bakery domain DNS -> HTTPS website delivery (other, DNS alias): Resolves bakery domain to CloudFront
  - satisfies: R3
- HTTPS website delivery -> Private static website files (origin, HTTPS): Fetches static site files from private bucket
  - satisfies: R1, R2, R6, R7
- HTTPS certificate -> HTTPS website delivery (other): Certificate attached for custom-domain HTTPS
  - satisfies: R3
- HTTPS website delivery -> Operational monitoring (write): Delivery metrics and configured logs
  - satisfies: R4, R6

## Scenario: nightly-reports-serverless

**User prompt**

> Every night at 02:00 we need to generate PDF sales reports from our existing Aurora PostgreSQL database, store them for a year, and email a download link to 40 regional managers. The job takes about 25 minutes. Keep it simple and cheap.

**Enabled priorities** (chosen by the user with one-click toggles)

- Prefer serverless and fully managed services (Lambda, API Gateway, DynamoDB, Fargate, Step Functions) over servers to manage.

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Generate PDF sales reports every night at 02:00 from the existing Aurora PostgreSQL database
- R2 [non-functional, confirmed] Store generated reports for one year
- R3 [functional, confirmed] Email a download link to 40 regional managers after each report is generated
- R4 [non-functional, confirmed] Report generation job takes about 25 minutes per run
- R5 [constraint, confirmed] Keep the solution simple and low cost
- R6 [non-functional, inferred] Scheduled job must complete within a nightly window starting at 02:00 without requiring always-on compute
- R7 [non-functional, inferred] Download links should expire and access to reports should be restricted to intended recipients
- R8 [constraint, inferred] Access to Aurora PostgreSQL must be read-only and network-secured within the existing VPC
- R9 [non-functional, inferred] Automatically delete reports after one year to control storage cost
- R10 [non-functional, confirmed] Prefer serverless and fully managed services (Lambda, API Gateway, DynamoDB, Fargate, Step Functions) over servers to manage.
- R11 [functional, inferred] Failed or incomplete nightly runs must be detected and alerted on so managers are not silently left without reports
- R12 [non-functional, inferred] Re-running the same night's job must not send duplicate emails or overwrite a completed report for that date

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - AWS Region (region) [C2]
    - Existing VPC (vpc) [C3]
      - Public subnet (subnet, public) [C4]
      - Private subnet (subnet, private) [C5]

**Nodes**

- **EventBridge Scheduler 02:00 trigger** [N1] - service: Amazon EventBridge
  - purpose: Starts the nightly report run at 02:00 each day
  - rationale: EventBridge scheduling is serverless and needs no always-on compute
  - placed in: AWS Region
  - satisfies: R1, R6
- **Step Functions report workflow** [N2] - service: AWS Step Functions
  - purpose: Runs the report task, waits for completion, retries on failure, then triggers notification
  - rationale: Step Functions handles the 25-minute job with state tracking and retries without a long-running Lambda
  - placed in: AWS Region
  - satisfies: R1, R3, R4, R6, R10, R11, R12
- **Fargate PDF report task** [N3] - service: AWS Fargate
  - purpose: Queries Aurora read-only, renders one PDF per region and writes it to S3
  - rationale: Fargate runs the roughly 25-minute job serverlessly, avoiding the Lambda 15-minute limit and any server management
  - placed in: Private subnet
  - satisfies: R1, R4, R5, R6, R8, R10, R12
- **Existing Aurora PostgreSQL** [N4] - service: Amazon Aurora
  - purpose: Source of sales data, accessed with a read-only role
  - rationale: Existing database is reused as the report source; access is restricted to the private subnet
  - placed in: Private subnet
  - satisfies: R1, R8
- **Database credentials secret** [N5] - service: AWS Secrets Manager
  - purpose: Holds the read-only Aurora credentials retrieved by the Fargate task at run time
  - rationale: Keeps database credentials out of task definitions and code
  - placed in: AWS Region
  - satisfies: R8
- **Report bucket** [N6] - service: Amazon S3
  - purpose: Stores generated PDF reports for one year before automatic deletion
  - rationale: S3 is durable, low-cost storage with lifecycle expiration to meet the one-year retention and cost goals
  - placed in: AWS Region
  - configuration encryption: AWS-managed
  - satisfies: R2, R7, R9, R10, R12
- **Notifier Lambda** [N7] - service: AWS Lambda
  - purpose: Creates a presigned download URL for each manager and sends the email
  - rationale: Short, event-driven email step fits Lambda well and is invoked after the report completes
  - placed in: AWS Region
  - satisfies: R3, R7, R10, R11
- **Amazon SES** [N8] - service: Amazon SES
  - purpose: Sends the download-link email to the 40 regional managers
  - rationale: SES is the low-cost managed email service for transactional email
  - placed in: AWS Region
  - satisfies: R3, R5
- **Regional managers (40)** [N9] - EXTERNAL third-party: Regional managers (40)
  - purpose: Recipients who download their regional PDF reports
  - rationale: Recipients of the email link
  - satisfies: R3, R7
- **NAT Gateway** [N10] - service: NAT Gateway
  - purpose: Provides outbound internet access for the private Fargate task to reach AWS APIs
  - rationale: Needed so the private task can call SES, Secrets Manager and Step Functions
  - placed in: Public subnet
  - satisfies: R5, R6, R8
- **CloudWatch logs and alarms** [N11] - service: Amazon CloudWatch
  - purpose: Collects task and workflow logs and alarms on failed executions
  - rationale: Observability for the nightly job and detection of failed runs
  - placed in: AWS Region
  - satisfies: R1, R4, R11

**Edges**

- EventBridge Scheduler 02:00 trigger -> Step Functions report workflow (invoke): Starts nightly run at 02:00
  - satisfies: R1, R6
- Step Functions report workflow -> Fargate PDF report task (invoke): Runs report task and waits for completion
  - satisfies: R4, R6, R12
- Fargate PDF report task -> Existing Aurora PostgreSQL (read, PostgreSQL 5432): Read-only sales queries
  - satisfies: R1, R8
- Fargate PDF report task -> Database credentials secret (read, HTTPS): Retrieves read-only credentials
  - satisfies: R8
- Fargate PDF report task -> Report bucket (write, HTTPS): Stores PDF reports
  - satisfies: R2, R9, R12
- Step Functions report workflow -> Notifier Lambda (invoke): Triggers notification after report is stored
  - satisfies: R3, R11
- Notifier Lambda -> Report bucket (read, HTTPS): Generates presigned download URLs
  - satisfies: R7
- Notifier Lambda -> Amazon SES (invoke, HTTPS): Sends download-link emails
  - satisfies: R3, R7
- Amazon SES -> Regional managers (40) (other): Email with expiring download link
  - satisfies: R3, R7
- Fargate PDF report task -> NAT Gateway (other): Outbound traffic to AWS APIs
  - satisfies: R5, R6
- Step Functions report workflow -> CloudWatch logs and alarms (other): Workflow logs and failure alarm
  - satisfies: R4, R11

**Nodes**

- **EventBridge Scheduler 02:00 trigger** [N1] - service: Amazon EventBridge
  - purpose: Starts the nightly report run at 02:00 each day
  - rationale: EventBridge scheduling is serverless and needs no always-on compute
  - placed in: AWS Region
  - satisfies: R1, R6
- **Step Functions report workflow** [N2] - service: AWS Step Functions
  - purpose: Runs the report task, waits for completion, retries on failure, then triggers notification
  - rationale: Step Functions handles the 25-minute job with state tracking and retries without a long-running Lambda
  - placed in: AWS Region
  - satisfies: R1, R3, R4, R6, R10, R11, R12
- **Fargate PDF report task** [N3] - service: AWS Fargate
  - purpose: Queries Aurora read-only, renders one PDF per region and writes it to S3
  - rationale: Fargate runs the roughly 25-minute job serverlessly, avoiding the Lambda 15-minute limit and any server management
  - placed in: Private subnet
  - satisfies: R1, R4, R5, R6, R8, R10, R12
- **Existing Aurora PostgreSQL** [N4] - service: Amazon Aurora
  - purpose: Source of sales data, accessed with a read-only role
  - rationale: Existing database is reused as the report source; access is restricted to the private subnet
  - placed in: Private subnet
  - configuration encryption: AWS-managed
  - satisfies: R1, R8
- **Database credentials secret** [N5] - service: AWS Secrets Manager
  - purpose: Holds the read-only Aurora credentials retrieved by the Fargate task at run time
  - rationale: Keeps database credentials out of task definitions and code
  - placed in: AWS Region
  - satisfies: R8
- **Report bucket** [N6] - service: Amazon S3
  - purpose: Stores generated PDF reports for one year before automatic deletion
  - rationale: S3 is durable, low-cost storage with lifecycle expiration to meet the one-year retention and cost goals
  - placed in: AWS Region
  - configuration encryption: AWS-managed
  - satisfies: R2, R7, R9, R10, R12
- **Notifier Lambda** [N7] - service: AWS Lambda
  - purpose: Creates a presigned download URL for each manager and sends the email
  - rationale: Short, event-driven email step fits Lambda well and is invoked after the report completes
  - placed in: AWS Region
  - satisfies: R3, R7, R10, R11
- **Amazon SES** [N8] - service: Amazon SES
  - purpose: Sends the download-link email to the 40 regional managers
  - rationale: SES is the low-cost managed email service for transactional email
  - placed in: AWS Region
  - satisfies: R3, R5
- **Regional managers (40)** [N9] - EXTERNAL third-party: Regional managers (40)
  - purpose: Recipients who download their regional PDF reports
  - rationale: Recipients of the email link
  - satisfies: R3, R7
- **NAT Gateway** [N10] - service: NAT Gateway
  - purpose: Provides outbound internet access for the private Fargate task to reach AWS APIs
  - rationale: Needed so the private task can call SES, Secrets Manager and Step Functions
  - placed in: Public subnet
  - satisfies: R5, R6, R8
- **CloudWatch logs and alarms** [N11] - service: Amazon CloudWatch
  - purpose: Collects task and workflow logs and alarms on failed executions
  - rationale: Observability for the nightly job and detection of failed runs
  - placed in: AWS Region
  - satisfies: R1, R4, R11

**Edges**

- EventBridge Scheduler 02:00 trigger -> Step Functions report workflow (invoke): Starts nightly run at 02:00
  - satisfies: R1, R6
- Step Functions report workflow -> Fargate PDF report task (invoke): Runs report task and waits for completion
  - satisfies: R4, R6, R12
- Fargate PDF report task -> Existing Aurora PostgreSQL (read, PostgreSQL 5432): Read-only sales queries
  - satisfies: R1, R8
- Fargate PDF report task -> Database credentials secret (read, HTTPS): Retrieves read-only credentials
  - satisfies: R8
- Fargate PDF report task -> Report bucket (write, HTTPS): Stores PDF reports
  - satisfies: R2, R9, R12
- Step Functions report workflow -> Notifier Lambda (invoke): Triggers notification after report is stored
  - satisfies: R3, R11
- Notifier Lambda -> Report bucket (read, HTTPS): Generates presigned download URLs
  - satisfies: R7
- Notifier Lambda -> Amazon SES (invoke, HTTPS): Sends download-link emails
  - satisfies: R3, R7
- Amazon SES -> Regional managers (40) (other): Email with expiring download link
  - satisfies: R3, R7
- Fargate PDF report task -> NAT Gateway (other): Outbound traffic to AWS APIs
  - satisfies: R5, R6
- Step Functions report workflow -> CloudWatch logs and alarms (other): Workflow logs and failure alarm
  - satisfies: R4, R11
