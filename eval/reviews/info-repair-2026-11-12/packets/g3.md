# Review packet, group 3

Scenarios in this packet: myblog-backups, claims-approval-workflow, product-search-cost. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: myblog-backups

**User prompt**

> We need a serverless global blog. Traffic is read-heavy with infrequent writes. Static site plus a REST API, with caching. New subscribers get a welcome email. Authors upload photos and we need thumbnails. Keep latency and cost low.

**Enabled priorities** (chosen by the user with one-click toggles)

## Scenario: claims-approval-workflow

**User prompt**

> Customers submit insurance claims with photos and PDF documents through a web form. Each claim goes through automated checks, then waits up to 14 days for an adjuster to approve or reject it, then the customer is emailed the decision. Every step must be auditable and the process must resume correctly after failures.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Customers submit insurance claims through a web form
- R2 [functional, confirmed] Claims can include photos and PDF documents
- R3 [functional, confirmed] Each claim goes through automated checks
- R4 [functional, confirmed] Each claim waits up to 14 days for an adjuster to approve or reject it
- R5 [functional, confirmed] Customer is emailed the adjuster's decision
- R6 [non-functional, confirmed] Every step of the claim process must be auditable
- R7 [non-functional, confirmed] The process must resume correctly after failures without losing or duplicating claim state
- R8 [functional, inferred] Long-running claim workflow must support a human approval step with a 14-day timeout
- R9 [non-functional, inferred] Uploaded photos and PDFs must be stored durably and linked to their claim
- R10 [constraint, inferred] Audit records must be immutable and retained for later review
- R11 [functional, inferred] Adjuster needs a way to receive pending claims and record a decision
- R12 [functional, inferred] Customer uploads should be validated for allowed file types before automated checks run
- R13 [non-functional, inferred] Automated checks, audit writes and decision recording must be idempotent so retries after failures do not duplicate claim state or emails
- R14 [constraint, inferred] Adjuster review endpoints must be restricted to authenticated internal staff
- R15 [non-functional, inferred] Uploads must be limited in size and type, and customer upload URLs must be short-lived

## Scenario: product-search-cost

**User prompt**

> Our e-commerce site has 2 million products in a relational database that stays the source of truth. Shoppers need fast full-text search with typo tolerance and filters (brand, price, size). Product pages are read far more often than they change, and price updates must appear in search within a minute. The web API runs in containers.

**Enabled priorities** (chosen by the user with one-click toggles)

- Minimize cost: choose the cheapest reasonable options and scale to zero where possible.

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [constraint, confirmed] The relational database is the source of truth for product data.
- R2 [functional, confirmed] The catalog contains 2 million products.
- R3 [functional, confirmed] Shoppers need fast full-text product search with typo tolerance.
- R4 [functional, confirmed] Search results must support filters for brand, price, and size.
- R5 [non-functional, confirmed] Price updates must appear in search within one minute.
- R6 [non-functional, confirmed] Product pages are read much more often than they change.
- R7 [constraint, confirmed] The web API runs in containers.
- R8 [functional, inferred] Searchable product data must be indexed separately from the relational source of truth, with changes propagated to the index.
- R9 [functional, inferred] What shopper traffic should the search and product-page workloads support? (decided by the architect)
- R10 [functional, inferred] What availability target should apply to search and product pages? (decided by the architect)
- R11 [non-functional, confirmed] Minimize cost: choose the cheapest reasonable options and scale to zero where possible.
- R12 [non-functional, inferred] Support a modest initial shopper load with horizontal scaling and a path to increase capacity as traffic grows; exact throughput is not specified.
- R13 [non-functional, inferred] Target 99.9% monthly availability for search and product pages, while recognizing that no deployment or recovery objective was specified.
- R14 [functional, inferred] Load the existing 2-million-product catalog into the search index initially, and provide a repeatable rebuild process from the relational source of truth.
- R15 [functional, inferred] Use a read cache for frequently requested product-page data, with a short time-to-live and invalidation or expiry after product changes.
- R16 [functional, inferred] Propagate relational product changes to search through a durable change-capture or outbox mechanism, with retries and monitoring to meet the one-minute price freshness target.
