# Review packet, group 6

Scenarios in this packet: k8s-microservices-ha, mobile-backend, iot-telemetry. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: iot-telemetry

**User prompt**

> We manufacture 50,000 smart thermostats that publish temperature readings over MQTT every minute. We need secure device connectivity with per-device certificates, alerts to the owner by SMS when a reading is out of range, and a dashboard of the last 90 days per device.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [functional, confirmed] Support 50,000 smart thermostats publishing temperature readings over MQTT every minute.
- R2 [functional, confirmed] Provide secure device connectivity using per-device certificates.
- R3 [functional, confirmed] Send the thermostat owner an SMS alert when a reading is out of range.
- R4 [functional, confirmed] Provide a dashboard showing the last 90 days of readings for each device.
- R5 [functional, inferred] Associate devices and their readings with the correct owner so alerts and dashboard access can be scoped appropriately.
- R6 [functional, inferred] Evaluate readings against defined out-of-range thresholds to determine when to send alerts.
- R7 [functional, inferred] Retain and make readings queryable for at least 90 days to support the dashboard.
- R8 [functional, inferred] How should owners authenticate to the dashboard? (decided by the architect)
- R9 [functional, inferred] How many dashboard users should the system support, and approximately how many devices will each user manage? (decided by the architect)
- R10 [functional, inferred] Should readings be deleted after the 90-day dashboard window, or retained longer? (decided by the architect)

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]
  - Primary AWS Region (region) [C2]

**Nodes**

- **Thermostat fleet** [N1] - EXTERNAL client-app: 50,000 smart thermostats
  - purpose: Publishes temperature readings every minute over MQTT using per-device certificates.
  - rationale: Represents the deployed devices connecting to the managed IoT endpoint.
  - satisfies: R1, R2
- **AWS IoT Core** [N2] - UNRESOLVED service: AWS IoT Core
  - purpose: Terminates device MQTT connections and authenticates devices with their individual certificates.

  - satisfies: R1, R2
- **Reading and alert processor** [N3] - service: AWS Lambda
  - purpose: Validates readings, looks up device ownership and thresholds, writes readings to the time-series store, and sends alerts when readings are out of range.
  - rationale: Processes each IoT-routed reading without maintaining servers; uses the registry to scope alerts to the correct owner.
  - placed in: Primary AWS Region
  - satisfies: R1, R3, R5, R6, R7
- **Device and owner registry** [N4] - service: Amazon DynamoDB
  - purpose: Stores device-to-owner associations, owner phone numbers, and configured thresholds.
  - rationale: Provides a simple key-value registry for ownership and alert configuration lookups.
  - placed in: Primary AWS Region
  - configuration encryption: AWS-managed
  - satisfies: R3, R5, R6
- **Temperature readings** [N5] - UNRESOLVED service: Amazon Timestream for LiveAnalytics
  - purpose: Stores readings for dashboard queries over the most recent 90 days.
  - rationale: A managed time-series database fits timestamped, per-device readings and the specified 90-day query window.
  - placed in: Primary AWS Region
  - satisfies: R1, R4, R7
- **Owner SMS notifications** [N6] - service: Amazon SNS
  - purpose: Delivers out-of-range alert messages to the owner's registered phone number.
  - rationale: Amazon SNS supports programmatic SMS publishing from the reading processor.
  - placed in: Primary AWS Region
  - satisfies: R3, R5, R6
- **Owners** [N7] - EXTERNAL user: Thermostat owners
  - purpose: Receive SMS alerts and access the dashboard.
  - rationale: Represents users of the dashboard and recipients of alerts.
  - satisfies: R3, R4, R5, R8, R9
- **Owner sign-in** [N8] - service: Amazon Cognito
  - purpose: Authenticates dashboard owners.
  - rationale: Provides managed user authentication for the dashboard.
  - placed in: Primary AWS Region
  - satisfies: R4, R5, R8, R9
- **Dashboard API** [N9] - service: Amazon API Gateway
  - purpose: Provides authenticated endpoints for owners to query their devices and 90 days of readings.
  - rationale: A regional HTTP API fronts the dashboard backend and uses Cognito authorization.
  - placed in: Primary AWS Region
  - configuration apiType: HTTP
  - configuration authorizer: Cognito
  - satisfies: R4, R5, R7, R8, R9, R10
- **Dashboard query handler** [N10] - service: AWS Lambda
  - purpose: Checks the authenticated owner's device access and queries readings for selected devices and time ranges.
  - rationale: Keeps dashboard data access scoped to the owner rather than exposing the time-series store directly.
  - placed in: Primary AWS Region
  - satisfies: R4, R5, R7, R9, R10
- **Dashboard client** [N11] - EXTERNAL client-app: Owner web dashboard
  - purpose: Displays a device's temperature history for the last 90 days.
  - rationale: Represents the owner's browser-based dashboard.
  - satisfies: R4, R5, R8, R9, R10
- **Application observability** [N12] - service: Amazon CloudWatch
  - purpose: Collects service metrics and logs for monitoring ingestion, processing, dashboard requests, and alert delivery.
  - rationale: Provides baseline operational visibility into the application.
  - placed in: Primary AWS Region
  - satisfies: R1, R3, R4, R6, R7

**Edges**

- Thermostat fleet -> AWS IoT Core (invoke, MQTT over TLS): Publish readings with per-device certificates
  - satisfies: R1, R2

  - satisfies: R1, R6

  - satisfies: R5, R6

  - satisfies: R4, R8
- Owners -> Dashboard client (invoke, HTTPS): Use dashboard
  - satisfies: R4, R5, R9, R10
- Dashboard client -> Dashboard API (invoke, HTTPS): Request owner-scoped reading history
  - satisfies: R4, R5, R7

  - satisfies: R5, R8
- Dashboard API -> Dashboard query handler (invoke): Invoke dashboard query handler
  - satisfies: R4, R5, R7

  - satisfies: R5
- Dashboard query handler -> Temperature readings (read): Query selected device's readings within the 90-day window
  - satisfies: R4, R5, R7, R10
