# Review packet, group 9

Scenarios in this packet: myblog, saas-containers, saas-containers-multi-az. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

We do not want to manage Kubernetes or servers.

### Design A

**Requirements**

- R1 [functional, confirmed] Provide a REST API for a B2B SaaS application.

- R3 [functional, confirmed] Use a PostgreSQL database.
- R4 [functional, confirmed] Provide a shared session cache.
- R5 [non-functional, confirmed] The application must remain available through the loss of one Availability Zone.
- R6 [constraint, confirmed] Application containers must not be directly reachable from the internet.
- R7 [functional, confirmed] The application must be able to make outbound calls to a third-party payments API.
- R8 [functional, confirmed] Database credentials must be rotated automatically.
- R9 [constraint, confirmed] Run the containers without managing Kubernetes or servers.
- R10 [constraint, inferred] Use a managed container runtime and managed supporting services where practical, avoiding self-managed servers or Kubernetes.
- R11 [functional, inferred] Provide outbound network access for payments API calls while keeping the containers themselves inaccessible directly from the internet.
- R12 [functional, inferred] How should B2B clients authenticate to the REST API? (decided by the architect)
- R13 [functional, inferred] What workload should the service initially support? This affects capacity and scaling choices. (decided by the architect)
- R14 [non-functional, confirmed] Survive the loss of one Availability Zone: stateful services run Multi-AZ.
- R15 [functional, inferred] Authenticate B2B API clients using OAuth 2.0 client credentials, with client identities and scopes managed by Amazon Cognito.

### Design B

**Requirements**

- R1 [functional, confirmed] Provide a REST API for a B2B SaaS application.
- R2 [constraint, confirmed] Package the application as Docker containers.
- R3 [functional, confirmed] Use a PostgreSQL database.
- R4 [functional, confirmed] Provide a shared session cache.
- R5 [non-functional, confirmed] The application must remain available through the loss of one Availability Zone.
- R6 [constraint, confirmed] Application containers must not be directly reachable from the internet.
- R7 [functional, confirmed] The application must be able to make outbound calls to a third-party payments API.
- R8 [functional, confirmed] Database credentials must be rotated automatically.
- R9 [constraint, confirmed] Run the containers without managing Kubernetes or servers.
- R10 [constraint, inferred] Use a managed container runtime and managed supporting services where practical, avoiding self-managed servers or Kubernetes.
- R11 [functional, inferred] Provide outbound network access for payments API calls while keeping the containers themselves inaccessible directly from the internet.
- R12 [functional, inferred] How should B2B clients authenticate to the REST API? (decided by the architect)
- R13 [functional, inferred] What workload should the service initially support? This affects capacity and scaling choices. (decided by the architect)
- R14 [non-functional, confirmed] Survive the loss of one Availability Zone: stateful services run Multi-AZ.
- R15 [functional, inferred] Authenticate B2B API clients using OAuth 2.0 client credentials, with client identities and scopes managed by Amazon Cognito.
- R16 [non-functional, inferred] Begin with a modest, horizontally scalable workload; use service autoscaling and validate capacity through load testing before production.

**Containers** (tree)

- AWS (aws-cloud) [C1]
  - Primary Region (region) [C2]
    - Application VPC (vpc) [C3]

      - Availability Zone 2 (availability-zone) [C5]

**Nodes**

- **B2B API clients** [N1] - EXTERNAL client-app: B2B client applications
  - purpose: Call the REST API using OAuth 2.0 client credentials.
  - rationale: External clients are the API consumers.
  - satisfies: R1, R12, R15
- **Payments API** [N2] - EXTERNAL third-party: Third-party payments API
  - purpose: Receive outbound payment API calls from the application.
  - rationale: The payments API is a third-party network service.
  - satisfies: R7, R11
- **Public REST API** [N3] - service: Amazon API Gateway
  - purpose: Provide the public API endpoint and private integration to the application.
  - rationale: API Gateway provides REST ingress without exposing application containers directly.
  - placed in: Primary Region
  - configuration apiType: REST
  - configuration authorizer: Cognito user pool
  - satisfies: R1, R6, R12, R15
- **B2B client authentication** [N4] - service: Amazon Cognito
  - purpose: Manage B2B client identities and OAuth 2.0 client-credentials tokens and scopes.
  - rationale: Cognito supplies the chosen API client authentication mechanism.
  - placed in: Primary Region
  - satisfies: R12, R15
- **Internal application load balancer across both AZs** [N5] - service: Application Load Balancer
  - purpose: Route API Gateway private integration traffic to application tasks across both Availability Zones.
  - rationale: The internal ALB spans private subnets in both Availability Zones and provides a private target for the API Gateway VPC link.
  - placed in: Private application subnet 1
  - satisfies: R1, R5, R6, R9, R10
- **ECS service orchestration** [N6] - service: Amazon ECS
  - purpose: Manage the container service and its desired capacity.
  - rationale: ECS provides managed container orchestration without Kubernetes.
  - placed in: Primary Region
  - satisfies: R2, R9, R10, R13, R16
- **Private API tasks** [N7] - service: AWS Fargate
  - purpose: Run the Docker-packaged API in private subnets across both Availability Zones.
  - rationale: Fargate runs containers without managing servers; private subnet placement prevents direct internet reachability.
  - placed in: Private application subnet 1
  - satisfies: R2, R5, R6, R7, R9, R10, R11, R13, R16
- **Aurora PostgreSQL** [N8] - service: Amazon Aurora
  - purpose: Persist application relational data using PostgreSQL.
  - rationale: Aurora provides managed PostgreSQL-compatible storage with replicas across Availability Zones for failover.
  - placed in: Private application subnet 1
  - configuration encryption: AWS-managed
  - configuration multiAz: enabled
  - satisfies: R3, R5, R14
- **Database connection proxy** [N9] - service: Amazon RDS Proxy
  - purpose: Pool and manage application connections to Aurora PostgreSQL.
  - rationale: RDS Proxy supports managed database connection pooling and integration with Secrets Manager credentials.
  - placed in: Private application subnet 1
  - satisfies: R3, R8
- **Shared session cache** [N10] - service: Amazon ElastiCache
  - purpose: Provide shared session storage for application tasks.
  - rationale: ElastiCache provides a managed shared cache with replicas across Availability Zones for failover.
  - placed in: Private application subnet 1
  - configuration encryption: AWS-managed
  - configuration multiAz: enabled
  - satisfies: R4, R5, R14
- **Database credentials** [N11] - service: AWS Secrets Manager
  - purpose: Store database credentials and manage their automatic rotation.
  - rationale: Secrets Manager provides managed secret storage and rotation support.
  - placed in: Primary Region
  - satisfies: R8
- **AZ 1 outbound gateway** [N12] - service: NAT Gateway
  - purpose: Provide outbound internet access for private-subnet tasks in Availability Zone 1.
  - rationale: A NAT Gateway enables task egress without allowing unsolicited inbound internet connections.
  - placed in: Public subnet 1
  - satisfies: R5, R7, R11
- **AZ 2 outbound gateway** [N13] - service: NAT Gateway
  - purpose: Provide outbound internet access for private-subnet tasks in Availability Zone 2.

  - placed in: Public subnet 2
  - satisfies: R5, R7, R11
- **Application observability** [N14] - service: Amazon CloudWatch
