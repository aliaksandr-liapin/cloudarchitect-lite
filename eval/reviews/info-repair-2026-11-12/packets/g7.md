# Review packet, group 7

Scenarios in this packet: order-events-cross-region, product-search, myblog. Read `reviewer-instructions.md` for the task and the output format.

## Rubric

Score each design on seven dimensions, each 0-3 (0 = critical defect, 3 = production-grade for an MVP-level design).

| Dimension              | What is checked                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| requirementCoverage    | All explicit requirements are reflected; assumptions are marked              |
| serviceFitness         | Service choices are justified; nothing redundant or expensive without reason |
| connectionCorrectness  | Direction, semantics, protocols and integrations are correct                 |
| securityBaseline       | Auth, least privilege, private data not public, encryption                   |
| reliabilityOperability | Error handling, DLQs, observability, fault tolerance                         |
| costAwareness          | No obvious overspend; serverless/managed where appropriate                   |
| explanationAccuracy    | Rationale and connection descriptions are technically correct                |

**Critical defect:** any dimension scored 0, or any incorrect technical statement that would lead the user to an insecure or non-working solution.

**Defect severities:** `minor` (cosmetic or small improvement), `major` (a real weakness or wrong detail that a careful architect would fix before building), `critical` (see above).

**Documentation rule:** every `major` or `critical` defect must cite an official AWS documentation or Well-Architected URL in its `evidence` field. A claim you cannot support with documentation should be recorded as `minor`.

## Scenario: order-events-cross-region

**User prompt**

> An online shop accepts orders through an API. After an order is placed, payment capture, inventory reservation and the confirmation email must happen independently, so a failure in one does not block the others. Failed steps must be retried and never silently lost. Orders are looked up by order ID.

**Enabled priorities** (chosen by the user with one-click toggles)

- Recover in a second AWS Region: data is replicated cross-region and the design can be restored there.

**Clarification answers given**

- (none)

## Scenario: myblog

**User prompt**

> We need a serverless global blog. Traffic is read-heavy with infrequent writes. Static site plus a REST API, with caching. New subscribers get a welcome email. Authors upload photos and we need thumbnails. Keep latency and cost low.

**Enabled priorities** (chosen by the user with one-click toggles)

- (none)

**Clarification answers given**

The tool asked the user up to three clarifying questions (listed among the requirements of each design). The user answered "You decide" to every question, so the architect chose.

### Design A

**Requirements**

- R1 [constraint, confirmed] Serverless global blog
- R2 [non-functional, confirmed] Traffic is read-heavy with infrequent writes
- R3 [functional, confirmed] Serve a static site plus a REST API
- R4 [non-functional, confirmed] Use caching to reduce read latency and load
- R5 [functional, confirmed] Send a welcome email to new subscribers
- R6 [functional, confirmed] Authors can upload photos
- R7 [functional, confirmed] Generate thumbnails for uploaded photos
- R8 [non-functional, confirmed] Keep latency low for globally distributed readers
- R9 [non-functional, confirmed] Keep operating cost low
- R10 [non-functional, inferred] Serve content globally with low latency through edge distribution
- R11 [non-functional, inferred] Scale automatically with traffic without managing servers
- R12 [functional, inferred] Handle author writes (posts and metadata) durably
- R13 [non-functional, inferred] Process image uploads asynchronously so authors are not blocked by thumbnail generation
- R14 [constraint, inferred] Restrict write operations to authenticated authors
- R15 [functional, inferred] Trigger subscriber welcome email on subscription event
- R16 [functional, inferred] How should authors and subscribers sign in? (decided by the architect)
- R17 [functional, inferred] What is the expected number of readers and subscribers, and how many authors write content? (decided by the architect)
- R18 [functional, inferred] What availability level does the blog need? (decided by the architect)
- R19 [constraint, inferred] Authors must be authenticated before uploading photos or writing posts, using Cognito user pool tokens checked at API Gateway
- R20 [non-functional, inferred] Thumbnail generation must be idempotent and retry-safe so repeated S3 events do not create duplicate or inconsistent thumbnails
- R21 [non-functional, inferred] Failed welcome-email sends and failed thumbnail jobs must be captured in a dead-letter queue and monitored with alarms
- R22 [non-functional, inferred] Observability of API, Lambda and queue health through CloudWatch metrics, logs and alarms
- R23 [non-functional, inferred] Public blog content must be protected against abusive traffic at the edge

**Containers** (tree)

- AWS Cloud (aws-cloud) [C1]

  - rationale: Edge caching and TLS termination reduce latency and origin load for read-heavy traffic
  - placed in: AWS Cloud
  - satisfies: R3, R4, R8, R9, R10, R17, R18, R23
- **AWS WAF** [N4] - service: AWS WAF
  - purpose: Filters abusive traffic at the edge for the blog and API
  - rationale: Protects the public entry point; attached to the CloudFront distribution
  - placed in: Primary Region
  - satisfies: R14, R23

  - purpose: Stores the static blog site assets, private behind OAC
  - rationale: Low-cost, durable hosting for static content
  - placed in: Primary Region
  - configuration encryption: AWS-managed
  - satisfies: R3, R9, R18

  - placed in: Primary Region

  - configuration authorizer: Cognito user pool
  - satisfies: R1, R3, R11, R14, R17, R18

  - purpose: Authenticates authors and subscribers
  - rationale: Managed sign-in issuing tokens checked by API Gateway
  - placed in: Primary Region
  - satisfies: R14, R16, R17, R18, R19
- **Blog API handler** [N9] - service: AWS Lambda
  - purpose: Handles post CRUD, subscriptions and presigned upload URL issuance
  - rationale: Serverless compute scales with traffic and avoids managing servers
  - placed in: Primary Region
  - satisfies: R6, R9, R11, R12, R17, R18
- **Posts and subscribers table** [N10] - service: Amazon DynamoDB
  - purpose: Durably stores posts, metadata and subscriber records
  - rationale: Serverless key-value store with on-demand capacity suits infrequent writes
  - placed in: Primary Region

  - configuration encryption: AWS-managed

  - rationale: Decouples uploads from processing so authors are not blocked
  - placed in: Primary Region
  - configuration deadLetterQueue: thumbnail-dlq
  - configuration encryption: AWS-managed
  - satisfies: R7, R13, R21
- **Thumbnail dead-letter queue** [N12] - service: Amazon SQS
  - purpose: Holds thumbnail jobs that repeatedly fail
  - rationale: Preserves failed jobs for inspection and retry
  - placed in: Primary Region
  - configuration encryption: AWS-managed
  - satisfies: R7, R21
- **Thumbnail generator** [N13] - service: AWS Lambda
  - purpose: Creates thumbnails from uploaded photos idempotently
  - rationale: Asynchronous serverless processing scales with upload volume
  - placed in: Primary Region
  - satisfies: R7, R13, R20
- **Welcome email dead-letter queue** [N14] - service: Amazon SQS
  - purpose: Captures welcome email tasks that fail after retries
  - rationale: Keeps failed welcome emails for replay and alarms
  - placed in: Primary Region
  - configuration encryption: AWS-managed
  - satisfies: R5, R15, R21
- **Welcome email sender** [N15] - service: AWS Lambda
  - purpose: Sends a welcome email when a subscriber record is created
  - rationale: Triggered by the subscriber stream so the email follows the committed write
  - placed in: Primary Region
  - satisfies: R5, R15, R17
- **Amazon SES** [N16] - service: Amazon SES
  - purpose: Sends welcome emails to new subscribers
  - rationale: Low-cost managed email sending
  - placed in: Primary Region
  - satisfies: R5, R9, R17
- **CloudWatch** [N17] - service: Amazon CloudWatch
  - purpose: Metrics, logs and alarms for API, Lambda, queues and DLQ depth
  - rationale: Observability for operating the blog and alerting on failures
  - placed in: Primary Region
  - satisfies: R12, R18, R21, R22

### Design B

**Requirements**

- R1 [constraint, confirmed] Serverless global blog
- R2 [non-functional, confirmed] Traffic is read-heavy with infrequent writes
- R3 [functional, confirmed] Serve a static site plus a REST API
- R4 [non-functional, confirmed] Use caching to reduce read latency and load
- R5 [functional, confirmed] Send a welcome email to new subscribers
- R6 [functional, confirmed] Authors can upload photos
- R7 [functional, confirmed] Generate thumbnails for uploaded photos
- R8 [non-functional, confirmed] Keep latency low for globally distributed readers
- R9 [non-functional, confirmed] Keep operating cost low
- R10 [non-functional, inferred] Serve content globally with low latency through edge distribution
- R11 [non-functional, inferred] Scale automatically with traffic without managing servers
- R12 [functional, inferred] Handle author writes (posts and metadata) durably
- R13 [non-functional, inferred] Process image uploads asynchronously so authors are not blocked by thumbnail generation
- R14 [constraint, inferred] Restrict write operations to authenticated authors
- R15 [functional, inferred] Trigger subscriber welcome email on subscription event
- R16 [functional, inferred] How should authors and subscribers sign in? (decided by the architect)
- R17 [functional, inferred] What is the expected number of readers and subscribers, and how many authors write content? (decided by the architect)
- R18 [functional, inferred] What availability level does the blog need? (decided by the architect)
- R19 [constraint, inferred] Authors must be authenticated before uploading photos or writing posts, using Cognito user pool tokens checked at API Gateway
- R20 [non-functional, inferred] Thumbnail generation must be idempotent and retry-safe so repeated S3 events do not create duplicate or inconsistent thumbnails
- R21 [non-functional, inferred] Failed welcome-email sends and failed thumbnail jobs must be captured in a dead-letter queue and monitored with alarms
- R22 [non-functional, inferred] Observability of API, Lambda and queue health through CloudWatch metrics, logs and alarms
- R23 [non-functional, inferred] Public blog content must be protected against abusive traffic at the edge
